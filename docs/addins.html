Architecture

Load order is the TOC: Core first, then feature modules, class modules, Dashboard last. Modules never call each other's internals; they register for game events and internal messages, write raw observations to their own saved namespace, and compute derived numbers at report time. Everything that leaves the game goes through the SavedVariables file.

How an add-in is written

A module is one Lua file registered with the core. It declares its saved namespace, the events and internal messages it wants, its commands, and optionally a HUD tab with buttons. The core wraps every handler in FO.Try, so a broken add-in logs an error and keeps the rest running. This is the whole contract:

local ADDON, FO = ...
local print = FO:Printer("Grinding")

local M = FO:NewModule("Grinding.MyThing", {
    account  = "mything",                 -- account-wide namespace -> self.db
    defaults = { log = {}, settings = { on = true } },
    -- char = "mything", cdefaults = {}   -- per-character -> self.cdb

    events = {                            -- game events
        PLAYER_TARGET_CHANGED = function(self) ... end,
    },
    messages = {                          -- internal messages from other modules
        FO_CL_DAMAGE = function(self, ev) ... end,   -- combat log adapter
        FO_SESSION_END = function(self, s) ... end,
    },
    commands = {
        mything = { help = "[reset] - what it shows", fn = function(self, arg) print("...") end },
    },
})

function M:OnEnable()                     -- PLAYER_LOGIN
    FO.Dashboard:RegisterTab("MyThing", 2.5, function() return self:Lines() end,
        function() return { { label = "Reset", fn = function() self.db.log = {} end } } end)
end
function M:OnTick(now) end               -- once a second, only if defined
function M:Lines() return { "|cffffd100MyThing|r  12 things/hr" } end

Add the file to the TOC in its area, add a test block to test/run.lua (the stub fakes the client, fires events and reads chat output), and open a pull request. CI runs the syntax check, the harness, the rotation data validation and the packaging step.

Conventions worth knowing

RuleWhy
Raw observations, derived at report timeFormulas change; encounters, loot rows, price snapshots and sessions never do. /fo dbstats shows namespace sizes; every log is capped.
Sample sizes on every estimateDrop rates use a Wilson interval; zone rankings carry a confidence label and low-confidence rows are down-weighted.
Your own recordings beat the seedA quest giver position you saw wins over the database; a measured kill time wins over the rotation estimate.
No protected automationOnly user-triggered actions. Auto-sell uses an unprotected API and can be switched off.
Degrade, never breakThe combat log, the map data provider and QuestieDB are all optional. Each module says what it is missing (/fo verify, /fo combatlog, /fo qdb, /fo map).
Everything has a chat command and a HUD lineThe Help tab and /fo manual are built from the live registry, so a new command documents itself.

Propose an add-in

What a good proposal says

  1. What it measures and the one number or line it would put on the HUD.
  2. Where the data comes from: a game event, a combat log event, an API call, or something the player types.
  3. What it saves and roughly how much per hour of play.
  4. Which existing module it is closest to, so it can reuse its namespace or messages.

Open one with the button at the top, or file an issue with the title prefix add-in:. Ideas without any of the above are still welcome; the open slots below show the shape.
